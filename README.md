# HK-Tunnel

Turn one SSH server into your own proxy. On Windows it takes over the system
proxy; on Android it takes over the whole device. No root, nothing to install
on the server.

把一台 SSH 服务器变成你自己的代理:Windows 上接管系统代理,Android 上接管全部流量。
两端共用同一台服务器、同一套账号密码,免 root,服务端不需要装任何东西。

## 两个版本

| 目录 | 平台 | 形态 |
|---|---|---|
| [`windows/`](windows/) | Windows 10 / 11 | PowerShell + WinForms,双击即用,可接管系统代理 |
| [`android/`](android/) | Android 8.0+ | 免 root 的 `VpnService` 全局代理,APK 见 [Releases](/seaunit/HK-Tunnel/releases) |

两边都是纯客户端:你只需要一台能 SSH 登录的服务器(任意发行版均可)。

## ⚠️ 使用前必读:这可能违反你服务器的服务商条款

这个工具做的事,在云厂商的语境里叫**流量穿透**(把服务器当代理/中转用)。它用的是标准
SSH 功能,但"技术上可行"不等于"条款上允许" —— 取决于**你那台服务器的服务商条款**。写在
这里是因为这个坑踩的人不少:

* **阿里云轻量应用服务器禁止用于流量穿透服务**,违规者**可能被关停并锁定实例**。这不是
  传言,阿里云开发者社区的说明文章里就是这么写的。锁定的后果不只是慢,是数据都可能拿不出来。
* 同一份说明还写着:标称带宽是**峰值上限而非保障带宽**,"在业务高峰期资源争抢时可能受到
  限制"。也就是说 200Mbps 的套餐不保证你能稳定跑 200Mbps。
* **把带宽拉满本身就是触发限速的动作**。公开案例(非个例):有人 200M 的东京轻量实例被限到
  20Mbps,TCP/UDP 一起限,约 48 小时后才恢复;有人拿同一类实例做中转,"持续 5Mbit 跑 1 小时
  就被限到 1~2M";还有反馈说继续重度使用会进一步限速,直到下一个计费周期。
* 风险是递进的:**限速 → 更严重的限速 → 关停并锁定实例**。

因此:

1. **别把"轻量/共享型"这类套餐当长期代理用**,尤其不要长时间拉满带宽。限速往往正是被拉满
   触发的,而限速之后的表现很有迷惑性:客户端只会告诉你"网络不可用",让人以为是工具坏了。
2. 如果当代理是刚需,选**允许该用途、且带宽是保障值**的实例:例如 **ECS 按固定带宽**
   (买多少是多少),或明确允许中转的服务商。
3. 条款会变,以你自己控制台上的最新条款为准;上面只是踩坑记录,不构成法律意见。

## 下载使用

### Android

1. 到 [Releases](/seaunit/HK-Tunnel/releases) 下载 `app-release.apk`
2. 传到手机上安装(会提示"未知来源",允许即可)
3. 填服务器地址、SSH 端口、登录用户、登录密码,点**连接**
4. 第一次会弹 VPN 授权,同意后状态变绿即全局生效
5. 通知栏和界面里都能断开

不勾「记住密码」时,密码只在这一条连接的生命周期内留在内存里;勾上则用
AndroidKeyStore 加密保存,只有这台设备能解回来。

### Windows

1. 下载本仓库(**Code → Download ZIP**,或 `git clone`)
2. 进入 `windows/`,双击 **`启动隧道.cmd`**
3. 填服务器地址、SSH 端口、登录用户、登录密码,点**启动隧道**

程序只依赖 Windows 自带的 OpenSSH 和 PowerShell 5.1+,没有第三方依赖。
目录里看不到 `hk-askpass.exe` / `hk-httpbridge.exe` 是正常的——它们由脚本在首次运行时
从源码即时编译生成,所以仓库里不放二进制。

自检:

```powershell
powershell -ExecutionPolicy Bypass -File windows\HK-Tunnel.ps1 -SelfTest
```

想让真实联调校验出口 IP 确实是你那台服务器,先设一个环境变量再跑
`-LiveTunnelSelfTest`(不设也能跑,只是改成校验三条路径出口一致):

```powershell
$env:HKTUNNEL_EXPECT_EXIT_IP = '<你的服务器公网 IP>'
```

### 浏览器突然上不了网怎么办

程序是靠**改写 Windows 系统代理**来接管流量的。如果它没能正常还原(比如被任务管理器强杀、
或程序本身启动失败),系统代理就会一直指着**已经关掉的本地桥接**,表现是浏览器打不开任何网页、
并提示"无法连接到代理服务器" —— 网络其实是好的。

一条命令就能救回来:

```powershell
powershell -ExecutionPolicy Bypass -File windows\HK-Tunnel.ps1 -ResetProxy
```

它会结束遗留的桥接进程、还原启动前的代理设置;即使备份文件已经丢失,也会直接把系统代理关掉。

### 备份里如果存的是我们自己的端口,就不还原它

有一种更隐蔽的坏状态:某次退出没走干净,系统代理已经指着 `127.0.0.1:1081`(本地桥接),
下一次启动时程序会把这份"启动前的原设置"照原样备份下来。等它再退出时,还原这份备份就等于
**把系统代理指回一个已经没人监听的端口** —— 而这恰恰会坑到那些"只在启动时读一次系统代理、
之后一直沿用"的程序(实测 Codex 桌面端就是这样):它们会在隧道停掉之后永远提示"等待网络",
而且**重启那个程序也没用**,因为启动那一刻读到的仍是那个死端口。

现在两头都堵上了:

* 写备份时,如果启动前的代理本来就指向本工具自己的端口(HTTP 桥接区间 `1081`–`1101`,
  或你自己的 SOCKS 端口),就把它记为"启动前代理是关的",不留这个死值。
* 还原时再挡一次:发现备份里是这类自指地址,就不还原它,而是**直接关掉系统代理**。

行为差异会在日志里写明(`restored-disabled`)。回归测试见
[`windows/tests/Test-ProxyRestoreGuard.ps1`](windows/tests/Test-ProxyRestoreGuard.ps1),
它同时验证"别人的代理(例如 `127.0.0.1:6478`)必须原样还原",避免误伤。

### 隧道断开会自动重拨

链路抖动、服务器重启、NAT 超时都会让后台的 `ssh.exe` 失效。程序每 5 秒核对一次隧道和桥接
是否还在,发现断了就自动重拨并重新接管系统代理;重拨前先还原系统代理,所以不会出现上面那种
"浏览器指向已经关闭的桥接"的状态。连续 20 次重拨仍失败才会放弃并提示。

另外,经桥接转发的长连接不会再被空闲超时掐断:静默几十秒的流式响应(长思考、SSE、
keep-alive 复用的 HTTPS 连接)是合法的,只有 TCP keep-alive 探测不到对端时才会回收。

### 停隧道之后,有的程序要重启一次

隧道运行期间,系统代理是 `127.0.0.1:1081`(本地 HTTP 桥接)。有些程序**只在启动那一刻**
读一次系统代理,之后就一直沿用那个值——实测 Codex 桌面端(以及它拉起的 `codex.exe`)就是
这样:它在隧道开着的时候启动,就把 `1081` 记死了。

于是隧道一停,`1081` 变成没人监听的死端口,这些程序会对每个请求立刻连接失败,界面一直显示
"等待网络/正在重连",而且**永远等不到**——因为它压根不会再去看已经还回去的系统代理。

处理办法很简单:把那个程序关掉重开一次。它重新读到的就是隧道退出时还原好的设置。

```powershell
# 例如 Codex:结束它的桌面端和后端进程,然后从开始菜单重新打开
Get-Process ChatGPT, codex -ErrorAction SilentlyContinue | Stop-Process -Force
```

反过来也成立:如果某程序必须在隧道开着时才能连外网(例如它要访问被墙的接口),那就先开隧道、
再开程序。

**同理,跑自检和测试也会踩这个坑。** `-SystemProxySelfTest` 以及 `windows/tests/` 下的
测试都会**临时**接管系统代理再还原;如果那类"只读一次"的程序恰好在测试窗口内启动,它就会把
临时端口记死,测试跑完依然连不上网。所以:跑测试时别同时用它们,跑完重启一次即可。

## 原理

```
应用流量 ──► 本地 SOCKS5 ──► SSH 动态转发 ──► 服务器 ──► 外网
                │
   Windows: 系统代理指向本地 HTTP 桥接(把 HTTP 代理转成 SOCKS5)
   Android: VpnService 建 tun 网卡,由 hev-socks5-tunnel 把 IP 包转成 SOCKS5
```

SSH 只负责一条加密长连接,服务器端做域名解析和实际建连,所以你不需要在服务器上
部署任何服务。

细节分别见 [`windows/`](windows/) 与 [`android/README.md`](android/README.md)。

## 已知限制

* **UDP 不过隧道。** SSH 端口转发本身只支持 TCP,这是协议决定的。走 QUIC 或纯 UDP
  的应用(部分视频通话、部分游戏)会回落到 TCP 或直接失败。
* **DNS 处理方式两端不同。** Android 端由内核里的映射 DNS 在本地合成假地址,再把
  原始域名交给服务器解析,查询不会泄漏到本地网络;Windows 端由 SOCKS5 客户端自己
  决定(浏览器通常开 `socks5h://` 走远端解析)。
* **服务端没有 IPv6 出口时**,Android 端会让 IPv6 直接走蜂窝网络而不是隧道,免得
  在隧道里反复失败。给服务器配上可用的 IPv6 后,把它重新收进隧道只需改一行。

## 安全说明

* 仓库**不包含**任何服务器地址、账号、密码或浏览器数据。连接信息保存在本机
  (`%LOCALAPPDATA%\HKTunnel`、Android 应用私有目录),不进版本库。
* 密码不会出现在命令行里:Windows 端通过环境变量交给 `ssh-askpass` 辅助程序,
  Android 端只在进程内存中传递,勾选"记住密码"时才用系统密钥库加密落盘。
* 服务器主机密钥首次连接时记录并固定,之后变更会被拒绝。
